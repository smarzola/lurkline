# Goal: Lurkline v0.2.0 Discovery, Search, And Inbox

Deliver a release-ready local v0.2.0 implementation in which humans and agents can discover Slack conversations, search workspace messages with bounded filters, address conversations by human-readable names, continue paginated reads, and obtain one bounded unread inbox snapshot without maintaining local state. ## Target State

When this goal is complete:

- Users and agents can list and find channels, DMs, and group DMs with stable typed metadata and enforced scan/result bounds.
- Users and agents can search messages with optional conversation and date filters, stable typed matches, deterministic newest-first ordering, and cursor/result bounds.
- Commands and tools that read a conversation accept either its Slack ID or an unambiguous exact human-readable name; IDs remain a zero-discovery fast path.
- Channel and thread reads accept Slack cursors and faithfully return the next cursor.
- One bounded inbox operation resolves unread conversation names and returns recent message context plus Slack’s unread-thread summary without marking anything read.
- The crate, MCP server, package metadata, tests, and task-oriented README consistently describe version 0.2.0 and its behavior.

## Constraints And Non-Goals

Follow `AGENTS.md`.

- Keep every Slack operation read-only and authenticated only from the existing environment configuration.
- Keep CLI and MCP behavior backed by the same typed service layer.
- Never commit, log, snapshot, or print real Slack credentials, HAR payloads, workspace messages, identifiers, or user data; tests and examples use synthetic fixtures.
- Preserve 0.1.0 command compatibility. Existing Slack IDs remain accepted without a conversation-list request.
- Enforce finite page sizes, scan limits, result limits, duplicate-cursor detection, response-size limits, and input validation.
- Conversation-name resolution is case-insensitive exact matching after an optional leading `#` or `@` is removed. Raw uppercase alphanumeric `C`-, `D`-, or `G`-prefixed values take ID precedence to preserve the no-discovery fast path; `#` or `@` explicitly forces name resolution for a colliding value. Missing and ambiguous names must fail rather than guess. Substring matching belongs only to the explicit find operation.
- Message search uses the read-only `search.messages` method. It accepts a non-empty query, optional ID-or-name conversation filter, optional validated `YYYY-MM-DD` `after`/`before` dates, an optional cursor, and a result limit from 1 through 100. It requests timestamp-descending results without highlights and exposes Slack-reported totals/cursors honestly.
- Inbox is a bounded, on-demand snapshot. It may read recent history for selected unread conversations and return Slack’s unread-thread counts, but must not infer exact unread message boundaries or thread roots that Slack did not provide.
- Do not add credential extraction, credential persistence, a cache/database, daemon, browser automation, writes, installers, shell completion, registry publication, tags, pushes, or GitHub releases.
- Implement the smallest coherent complete design. Prefer direct code and existing patterns over new dependencies, generalized repositories, caches, or speculative abstraction.

## Milestone 2: Bounded Message Search

Why this matters:

- Search lets humans and agents locate relevant Slack context without first knowing a conversation or timestamp.

Acceptance criteria:

- A typed shared-service operation calls `search.messages` with timestamp-descending order, highlights disabled, a maximum count of 100, and an optional continuation cursor.
- Optional conversation filtering resolves IDs or exact names and composes the appropriate Slack `in:` modifier; optional `after` and `before` values are strict calendar dates and invalid/reversed ranges fail before HTTP.
- Search matches normalize channel ID/name, timestamp, author identity, text, thread timestamp when available, and permalink without exposing response-only implementation details.
- Results expose Slack’s reported total, next cursor, and `has_more` truthfully across supported response-metadata locations.
- CLI `search messages` and MCP `slack_search_messages` use the shared service and matching defaults.
- Synthetic tests cover request shape, filter composition, empty results, limit/cursor handling, malformed matches/dates/cursors, and structured MCP errors.

Likely touchpoints (non-exhaustive):

- `src/model.rs`, `src/service.rs`, `src/http.rs`, `src/cli.rs`, `src/mcp.rs`, `tests/mcp_raw_stdio.rs`

Verification:

```bash
cargo fmt --check
cargo test search
cargo test --test mcp_raw_stdio
cargo clippy --all-targets -- -D warnings
```

Status: Complete on 2026-07-26. Because the sanitized HAR set has no search request, the transport follows Slack's documented legacy `search.messages` contract: cursor `*` starts pagination, `count` is capped at 100, `sort=timestamp`, `sort_dir=desc`, and `highlight=false`. Optional conversation and strict calendar-date filters are composed into the Slack query after exact typed resolution. Continuation is cursor-defined; the workspace total remains separately reported and does not falsely imply another page when the final cursor is absent. Verification passed: `cargo fmt --check`; `cargo test` (50 unit, 1 raw-stdio integration, 1 package integration); `cargo test search`; `cargo test --test mcp_raw_stdio`; `cargo clippy --all-targets -- -D warnings`; and `git diff --check`. Adversarial review found a repeated-cursor loop, whitespace-only cursor acceptance, terminal control-character exposure, and channel-only human notation. Repairs reject first/explicit cursor repetition, reject trim-empty input before I/O, centralize control escaping without changing JSON, and render C/D/G locations neutrally. Re-review reported no confirmed or blocking findings; live browser-session search compatibility remains the documented residual risk.
