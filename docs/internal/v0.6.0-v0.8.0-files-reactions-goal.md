## Target State

When this goal is complete:

- Agents can inspect message attachments, files, reactions, and workspace
  custom emoji without losing unknown Slack fields.
- Operators can download private Slack files without leaking browser
  credentials, following arbitrary redirects, clobbering files, traversing
  paths, or accepting unbounded content.
- Operators and explicitly enabled MCP agents can add and remove message
  reactions with deterministic postconditions and safe ambiguous-outcome
  handling.
- Operators and explicitly enabled MCP agents can stream one local regular
  file to Slack, share it to a root message or thread, and reconcile every
  multi-stage outcome without credential leakage or blind duplication.
- Lurkline can create and operate one-file Slack drafts without losing file
  references, deleting unrelated files, reposting after uncertain
  publication, or weakening the existing draft concurrency contract.
- `main` contains v0.8.0 after three sequential green pull requests, and tags
  `v0.6.0`, `v0.7.0`, and `v0.8.0` each have a successful native release with
  verified Linux x86-64, Linux ARM64, and macOS ARM64 assets.

## Constraints And Non-Goals

Follow `AGENTS.md`.

- Keep CLI and MCP behavior backed by the same typed service layer.
- Preserve v0.5.0 credential selection, file storage, discovery, inbox,
  rich-text reads, Markdown rendering, direct publication, and draft behavior.
- Never commit, log, snapshot, or print real Slack credentials, copied cURL
  commands, HAR payloads, workspace content, user file contents, or live IDs.
  Use synthetic fixtures and redacted structural notes only.
- Treat Slack messages, attachment fields, emoji metadata, filenames, MIME
  types, URLs, upload responses, and file bytes as private untrusted input.
- Preserve unknown message attachment and file metadata fields where the
  public result promises losslessness. Keep absence distinct from an explicit
  empty array.
- Treat legacy message attachments as read-only data. Do not add arbitrary
  attachment or Block Kit authoring.
- File downloads must use Slack-provided metadata and a fixed validated Slack
  origin policy. Do not accept caller-provided URLs. Never send the xoxc token
  or browser cookie to a raw upload URL, CDN, signed URL, redirect target, or
  non-workspace host unless a credential-safe observed Slack contract proves
  that exact transmission is required.
- Bound metadata responses, redirect hops, downloaded bytes, uploaded bytes,
  filenames, titles, alternative text, emoji names, file counts, and MCP
  payloads. Stream file bodies instead of buffering them completely.
- CLI downloads require an explicit output path and create a new owner-only
  regular file without overwrite. MCP file-system tools require an explicit
  absolute file root configured at server startup and accept only relative
  paths contained beneath that root.
- MCP upload additionally requires `--allow-write`; every Slack mutation
  requires `confirm: true`. Direct CLI mutations require `--confirm`.
- Resolve and validate all inputs before the first Slack mutation where
  possible. Preserve structured, secret-safe uncertain outcomes when a timeout,
  transport failure, HTTP failure, or malformed response can occur after Slack
  accepted a mutation.
- Reaction add/remove should be target-state idempotent: Slack's
  already-present or already-absent response is a successful no-change result,
  and ambiguous results are reconciled with an exact read when possible.
- Use Slack's current external-upload lifecycle. Do not call retired
  `files.upload`, base64-wrap local files for the Slack request, or buffer
  arbitrary files in MCP JSON.
- v0.7.0 supports one local regular file per upload to one root or thread
  destination. Batch uploads, snippets, remote files, public-link creation,
  file deletion, and scheduled uploads are non-goals.
- v0.8.0 supports one uploaded file per draft. Arbitrary legacy attachments,
  multiple destinations, multiple files, sent-message editing/deletion, and
  background upload cleanup are non-goals.
- Existing file drafts that cannot be proven safe under the observed Slack
  lifecycle must continue to fail closed and remain unchanged.
- Do not add a general HTTP client abstraction, storage daemon, background
  worker, local cache, credential helper, upload queue, or plugin system.
- Preserve unrelated user changes and use each required typed branch without
  stacking work on an unmerged release branch.
- Implement the smallest coherent design that completely satisfies this goal.
  Prefer direct code and established repository patterns. Do not add
  speculative abstractions, configuration, dependencies, or adjacent features.
- Simplicity must not omit required behavior, tests, error handling, live
  compatibility evidence, documentation, audit, or release verification.
