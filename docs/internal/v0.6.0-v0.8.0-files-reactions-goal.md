## Constraints And Non-Goals

Follow `AGENTS.md`.

- Keep CLI and MCP behavior backed by the same typed service layer.
- Preserve v0.5.0 credential selection, file storage, discovery, inbox,
  rich-text reads, Markdown rendering, direct publication, and draft behavior.
- Never commit, log, snapshot, or print real Slack credentials, copied cURL
  commands, HAR payloads, workspace content, user file contents, or live IDs.
  Use synthetic fixtures and redacted structural notes only.
- Treat Slack messages, attachment fields, emoji metadata, filenames, MIME
  types, URLs, upload responses, and file bytes as private untrusted input.
- Preserve raw message `attachments` losslessly, including unknown nested
  fields and the distinction between omission and an explicit empty array, on
  history, thread, exact-message, inbox, and search normalization paths.
  Existing `blocks` behavior remains lossless. File references, exact file
  metadata, reactions, and custom emoji use documented typed fields and make
  no lossless-unknown-field promise; reaction user IDs are explicitly
  potentially partial.
- Treat legacy message attachments as read-only data. Do not add arbitrary
  attachment or Block Kit authoring.
- File downloads must use Slack-provided metadata and a fixed validated Slack
  origin policy. Do not accept caller-provided URLs. Never send the xoxc token
  or browser cookie to a raw upload URL, CDN, signed URL, redirect target, or
  non-workspace host unless a credential-safe observed Slack contract proves
  that exact transmission is required.
- Bound metadata responses, redirect hops, downloaded bytes, uploaded bytes,
  filenames, titles, alternative text, emoji names, file counts, and MCP
  payloads. Stream file bodies instead of buffering them completely.
- Resolve local paths through directory descriptors. Open every existing path
  component relative to an already opened parent with no-follow semantics,
  require the expected directory or regular-file type, and never rely on a
  `canonicalize`-then-open check. CLI downloads require an explicit output path;
  MCP file-system tools require an explicit absolute file root configured at
  server startup and accept only relative paths contained beneath that root.
- For direct CLI calls, anchor an absolute path at an opened `/` descriptor and
  a relative path at an opened current-working-directory descriptor. For MCP,
  open the configured root once and anchor every operation there. Reject empty,
  `.`, and `..` components and symlinks at every level. CLI ancestors may have
  ordinary operator-selected permissions; the created file is always `0600`.
  MCP paths may not escape or replace their configured root.
- Create download temporary files with mode `0600` in the descriptor-anchored
  target directory. Stream and sync the complete bounded response before one
  atomic no-replace commit to the requested leaf, then sync the directory.
  Rename is the commit point: failure before it removes the temporary file and
  leaves no requested output; a directory-sync failure after it returns a
  successful download with a durability warning and never invites a duplicate
  retry. Existing destinations and ancestor/leaf symlinks fail without
  modification.
- Open uploads once through the descriptor-anchored path and require a regular
  file. Record descriptor identity, size, and metadata; stream a SHA-256
  preflight pass and a second upload pass while hashing; require matching
  digests plus stable identity, size, and metadata before completion. A
  mismatch after allocation returns a structured source-changed result and
  never completes or automatically reallocates the upload.
- MCP keeps every Slack mutation behind `--allow-write`. Preserve v0.5.0
  per-call confirmation behavior for text-draft create/update: they require the
  MCP write gate but no `confirm` field, and their direct CLI commands need no
  `--confirm`. New reaction add/remove, direct root/thread file upload, and
  file-draft creation require `confirm: true` or `--confirm`. Text updates to a
  supported file draft follow existing draft-update behavior without per-call
  confirmation. Draft deletion and publication retain their existing
  confirmation requirement.
- Resolve and validate all inputs before the first Slack mutation where
  possible. Preserve structured, secret-safe uncertain outcomes when a timeout,
  transport failure, HTTP failure, or malformed response can occur after Slack
  accepted a mutation.
- Reaction add/remove should be target-state idempotent: Slack's
  already-present or already-absent response is a successful no-change result,
  and ambiguous results are reconciled with an exact read when possible.
- Model uploads as explicit stages: `allocation_uncertain` has no recovery key;
  `allocated` has a non-secret file ID but no transferred bytes;
  `transfer_uncertain` has a file ID but unknown byte acceptance;
  `completion_uncertain` has a file ID and unknown share visibility; and
  `shared` is verified. Never automatically restart an uncertain allocation,
  never print, return, persist, or log a signed upload URL, and never claim an
  unreconcilable allocation was reconciled. Reconcile later stages only with
  the non-secret file ID and exact Slack reads when those reads can prove the
  target state. No general retry command is required.
- Use Slack's current browser-upload lifecycle. Do not call retired
  `files.upload`, base64-wrap local files for the Slack request, or buffer
  arbitrary files in MCP JSON.
- v0.7.0 supports one local regular file per upload to one root or thread
  destination. Batch uploads, snippets, remote files, public-link creation,
  file deletion, and scheduled uploads are non-goals.
- v0.8.0 supports one uploaded file per draft. Arbitrary legacy attachments,
  multiple destinations, multiple files, sent-message editing/deletion, and
  background upload cleanup are non-goals.
- A file draft is mutable across independent CLI/MCP processes only if current
  Slack state supplies a durable, exact association between that draft
  ID/revision and the file ID that is sufficient to prove the server will
  operate only on that draft-owned file. Uploader identity, private state, or
  lack of shares alone is never proof of exclusive draft ownership. Discovery
  must verify that predicate across a fresh invocation and the browser's exact
  delete/publication requests. If Slack exposes no sufficient durable proof,
  stop before v0.8.0 implementation and request a material design decision;
  do not introduce a provenance registry, weaken deletion behavior, or infer
  ownership silently.
- Existing file drafts that cannot satisfy that proven predicate must continue
  to fail closed and remain unchanged.
- Do not add a general HTTP client abstraction, storage daemon, background
  worker, local cache, credential helper, upload queue, or plugin system.
- Preserve unrelated user changes and use each required typed branch without
  stacking work on an unmerged release branch.
- Implement the smallest coherent design that completely satisfies this goal.
  Prefer direct code and established repository patterns. Do not add
  speculative abstractions, configuration, dependencies, or adjacent features.
- Simplicity must not omit required behavior, tests, error handling, live
  compatibility evidence, documentation, audit, or release verification.
