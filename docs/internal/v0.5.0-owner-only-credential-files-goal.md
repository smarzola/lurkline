# Goal: Deliver Lurkline v0.5.0 With Owner-Only Credential Files

Work in
`/Users/smarzola/Documents/Codex/2026-07-26/use-browser-to-read-sferait-ws/lurkline-v050`.

Release Lurkline v0.5.0 with a direct, agent-compatible credential backend:
one versioned JSON credential file per profile, stored beneath Lurkline's
platform configuration directory and restricted to its owner. Keep the
complete `SLACK_*` environment bundle as the only alternative credential
source. Do not add credential helpers or another secret-store abstraction.

Remove the native Keychain/keyring implementation completely, including its
direct dependencies, platform backend dependencies, tests, error paths, dead
code, CLI wording, user documentation, and obsolete internal design artifact.
Existing v0.4.1 profile registry metadata remains readable, but profiles
without a new credential file fail safely and tell the operator to re-import
them.

Source of truth: the user's request in the current Codex task.

## Target State

When this goal is complete:

- `lurkline auth import-curl --profile NAME` atomically stores a bounded,
  validated credential bundle in an owner-only per-profile file.
- Lurkline uses the complete environment bundle first, then the selected
  profile file; it implements no helper protocol and accesses no native secret
  store.
- Current code, tests, dependencies, help, package metadata, and user
  documentation contain no Keychain/keyring implementation or promise.
- v0.5.0 is merged to `main`, tagged, and published with verified Linux x86-64,
  Linux ARM64, and macOS ARM64 release archives and checksums.

## Constraints And Non-Goals

Follow `AGENTS.md`.

- Keep Slack read and guarded-write behavior unchanged.
- Never commit, log, snapshot, or print real Slack credentials or workspace
  data. Use synthetic fixtures only.
- Keep CLI and MCP behavior backed by the same typed service layer.
- Preserve the v0.4.1 profile registry schema, profile-selection precedence,
  cURL-import validation, and complete environment override.
- On macOS, store credentials under
  `~/Library/Application Support/lurkline/credentials/`; on Linux, store them
  under `$XDG_CONFIG_HOME/lurkline/credentials/` or
  `~/.config/lurkline/credentials/`.
- Require absolute `HOME` and `XDG_CONFIG_HOME` inputs. Map every validated
  profile bijectively to the lowercase hexadecimal encoding of its ASCII bytes
  plus `.json`. Names that differ only by case and names such as `.` and `..`
  must remain distinct ordinary leaf filenames on case-insensitive filesystems
  and must never select a directory or parent.
- Use a `0700` credentials directory and `0600` regular credential files on
  Unix. Validate the Lurkline configuration root, credentials directory,
  registry file, shared lock file, and credential files. Reject unsafe
  existing directories, symlinks, non-regular objects, wrong-owner objects,
  and permissions accessible to group or other users.
- Bound encoded credential bytes before writing and bytes read before parsing.
  Keep stored JSON versioned, normalized, deny unknown fields, and keep errors
  free of secret values.
- Serialize registry and credential changes across processes, use
  same-directory atomic replacement, sync committed writes, and preserve
  cross-file consistency or return an actionable reconciliation error.
- For handled errors, restore the last complete registry/file state whenever
  possible. A process or machine crash between two independent file commits
  may leave an orphan file, registry-only profile, or metadata mismatch; all
  such states fail closed, and a later import or remove retries and reconciles
  them without requiring a journal.
- Treat same-directory rename as the commit point. Sync file contents before
  rename and attempt to sync the containing directory afterward. A
  post-rename directory-sync failure must not be reported as an ordinary
  uncommitted failure that causes rollback after the new file is visible.
- Do not add credential helpers, helper configuration, native secret stores,
  encryption with an agent-readable colocated key, credential export, or
  migration that reads the retired backend.
- Do not capture browser credentials or perform a live Slack write as part of
  this goal; this release is verified with synthetic tests.
- Preserve unrelated user changes and work safely in the isolated worktree.
- Prefer direct code and existing patterns. Do not add speculative
  abstractions, extensibility, configuration, or adjacent features.
- Keep the implementation complete: simplicity must not omit required
  behavior, tests, error handling, compatibility guidance, or documentation.

## Success Criteria

The goal is complete only when:

1. Per-profile credential files use versioned normalized JSON, bounded reads,
   bounded writes, deterministic non-traversing filenames, owner-only paths,
   safe owner/mode/type checks, and atomic durable replacement.
2. Import, status, resolution, rotation, workspace replacement, concurrent
   operations, removal, and rollback preserve registry/file consistency and
   never expose credential material.
3. A complete `SLACK_*` bundle bypasses all profile storage; partial bundles
   fail atomically. Existing registry-only profiles fail safely with re-import
   guidance.
4. `keyring`, its platform store packages, the native-store implementation,
   native-store tests, direct Security-framework test dependency, retired
   errors, current help/docs, and the obsolete v0.3 design goal are removed.
5. No credential-helper protocol, command, configuration, or dependency is
   introduced.
6. Cargo, MCP metadata, CLI version expectations, install examples, and
   release packaging consistently report `0.5.0`.
7. Every milestone is checked off with verification evidence and a focused
   Conventional Commit checkpoint.
8. Final adversarial review, independent audit, full local verification, PR
   CI, merge, tag workflow, release object, six assets, and checksum readback
   all pass.
