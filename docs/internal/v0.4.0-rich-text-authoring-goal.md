## Target State

When this goal is complete:

- Every message read path retains Slack's complete `blocks` JSON alongside the
  existing fallback `text`, including unknown future block and element fields.
- A shared renderer converts a documented CommonMark subset to Slack
  `rich_text` blocks and a plain-text fallback without contacting Slack.
- Users can list, inspect, create, update, delete, and send Slack drafts for one
  root conversation or one existing thread.
- Users can send a root message or reply to a thread from Markdown. Every
  publication has a fresh `client_msg_id`, and thread broadcast is explicit.
- CLI and MCP use the same typed service. MCP writes are disabled unless the
  server starts with `--allow-write`; publication and deletion also require an
  explicit per-call confirmation.
- Existing discovery, inbox, search, message reads, authentication profiles,
  and environment overrides remain compatible.
- Package metadata, help, README, CLI behavior, MCP behavior, and tests
  consistently describe v0.4.0.
- Pull request checks, merge, tag workflow, release object, checksums, and the
  Linux x86_64, Linux arm64, and macOS arm64 archives are verified.

## Constraints And Non-Goals

Follow `AGENTS.md`.

- Preserve reads losslessly by carrying raw JSON values. Do not force unknown
  Slack blocks through a partial enum or silently rewrite read data.
- Render a bounded Markdown input using a documented subset: paragraphs,
  line breaks, emphasis, strong emphasis, strikethrough, inline code, fenced or
  indented code, links, block quotes, and ordered or unordered lists. Render
  headings as bold sections. Treat raw HTML as literal text. Reject empty or
  over-limit input before any Slack request.
- Generate only Slack `rich_text` blocks for authoring. Do not add an arbitrary
  Block Kit passthrough, attachments, files, scheduling, workflows, canvases,
  or multi-destination compose.
- Support exactly one conversation destination, either at its root or at an
  existing `thread_ts`. A broadcast flag is valid only for a thread reply.
- Treat private draft methods as compatibility-sensitive. Validate response
  shapes, bound lists and payloads, preserve server concurrency values, and
  return Slack's safe error code without leaking response bodies or secrets.
- Draft creation and update are explicit writes. Draft deletion and every send
  additionally require `--confirm` in the CLI or `confirm: true` in MCP.
- MCP starts write-disabled. `lurkline mcp --allow-write` is required for every
  draft mutation and publication. Read tools and local Markdown rendering
  remain available without it.
- A successful message post is never blindly retried. Draft publication sends
  first and deletes only after Slack confirms the post; if cleanup fails, return
  the sent message and an explicit cleanup warning so a caller cannot mistake
  the outcome and duplicate the message.
- A transport, timeout, HTTP, oversized-response, or malformed-acknowledgement
  result after publication begins is outcome-unknown, not a definitive failure.
  Return the generated client message ID and explicit do-not-retry guidance.
- Use fresh UUID v4 client message IDs for new draft and message requests.
- Keep the private browser-session credential model. Do not add bot/OAuth
  authorization, browser credential extraction, a daemon, or a database.
- Do not edit or delete sent messages, add reactions, upload files, schedule
  messages, or create conversations.
- Committed tests and fixtures use synthetic identifiers, messages, blocks,
  credentials, and responses only. Never commit, log, snapshot, or print real
  Slack tokens, cookies, HAR payloads, messages, drafts, or user data.
- Implement the smallest coherent complete design. CLI and MCP must not acquire
  separate rendering, validation, authorization, or publication semantics.

## Success Criteria

The goal is complete only when:

1. History, replies, exact-message lookup, inbox, and search retain raw `blocks`
   without data loss while preserving the v0.3.0 fields and pagination behavior.
2. The shared renderer produces deterministic Slack `rich_text` JSON and a
   bounded plain-text fallback for every documented Markdown construct, with
   synthetic golden and adversarial tests for nesting, Unicode, escapes, raw
   HTML, malformed input, empty input, and limits.
3. Draft list/get/create/update/delete validate IDs, destinations, revisions,
   limits, and response shapes; update uses a fresh edit timestamp and delete
   uses the fetched server revision converted to browser milliseconds.

   fresh `client_msg_id`, reject invalid broadcast combinations, and require
   explicit confirmation before network I/O.
5. Draft publication sends the stored rich blocks to its stored destination,
   avoids retry ambiguity, and reports post-success deletion failure as a
   successful send with a cleanup warning.
6. MCP is write-disabled by default, `--allow-write` gates all mutations, and
   destructive/publication calls require per-call confirmation. CLI and MCP
   expose equivalent typed results and safe errors.
7. Existing v0.3.0 commands, MCP read tools, credential profiles, environment
   overrides, and secret-redaction invariants remain compatible.
8. README follows Google developer documentation guidance and accurately
   documents Markdown support, stdin usage, drafts, safe root/thread sending,
   MCP write opt-in, private-API risk, and unsupported behavior.
9. Version fields, help, package metadata, CI/release configuration, and
   release archives consistently describe v0.4.0.
10. Formatting, lint, all synthetic tests, locked release build, CLI/MCP smoke,
    package checks, credential-pattern scan, and archive verification pass.
11. Every milestone is adversarially reviewed and committed with a focused

12. The pull request is green and merged, `v0.4.0` points at merged `main`, and
