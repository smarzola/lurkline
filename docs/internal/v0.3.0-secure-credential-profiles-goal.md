# Goal: Lurkline v0.3.0 Secure Credential Profiles

Work in `/Users/smarzola/Documents/Codex/2026-07-26/use-browser-to-read-sferait-ws/lurkline-auth`.

Deliver a release-ready local v0.3.0 implementation in which a user can import
an authenticated Slack browser request copied as cURL from standard input,
validate it, store the normalized browser-session credentials in the operating
system credential store under a named profile, and use that profile from both
the CLI and MCP server. Preserve the existing all-or-nothing environment
configuration as an explicit, non-persistent override.

Source of truth: the user-approved credential-helper design in the current
Codex task, the current repository behavior, and Chromium DevTools'
Copy-as-cURL output in `NetworkLogView.ts`.

## Target State

When this goal is complete:

- `pbpaste | lurkline auth import-curl --profile sferait` safely parses a
  bounded Chrome Copy-as-cURL request as data, validates the Slack session with
  a bounded read-only request, and stores only a normalized versioned
  credential bundle.
- `lurkline --profile sferait doctor`, every other Slack CLI command, and
  `lurkline --profile sferait mcp` resolve the same named profile.
- `lurkline auth list`, `auth status`, and `auth remove` manage profiles without
  revealing secrets. Re-import updates the same workspace profile; changing a
  profile to another workspace requires an explicit replacement flag.
- macOS uses Keychain and Linux uses Secret Service through the `keyring` crate.
  There is no plaintext credential fallback.
- `SLACK_BASE_URL`, `SLACK_TEAM_ID`, `SLACK_TOKEN`, and `SLACK_COOKIE` remain a
  supported highest-priority override. If any is set, all four are required;
  environment and stored credentials are never mixed.
- Secrets are redacted and zeroized where practical, are not unnecessarily
  cloned, and never appear in output, logs, errors, tests, fixtures, or Git.
- Package metadata, help text, README, CLI behavior, MCP behavior, and tests
  consistently describe v0.3.0.

## Constraints And Non-Goals

Follow `AGENTS.md`.

- Keep Slack access read-only. Import validation may use only the same bounded
  read-only doctor request as the shared service.
- Parse cURL input directly. Never invoke `curl`, a shell, `eval`, command
  substitution, sourced scripts, or any executable content from standard input.
- Bound cURL input to 256 KiB and reject malformed, incomplete, ambiguous, or
  non-Slack requests before network or credential-store access.
- Accept only an HTTPS root origin on a single-label `*.slack.com` host, a
  valid Slack team ID from `slack_route`, an `xoxc-` browser token from form
  data, and a cookie header containing a `d=` cookie. The `xoxc-` prefix is an
  import-only invariant; legacy environment tokens retain v0.2's non-empty,
  single-line validation so this feature does not break existing injection.
- Support current Chromium POSIX single-quoted and ANSI-C-quoted Copy-as-cURL
  output plus older positional URLs. Do not implement a general shell parser
  or execute shell semantics.
- Store one versioned credential bundle per profile using keyring service
  `me.smarzola.lurkline.slack-session` and the validated profile name as its
  account. Do not store the raw cURL request.
- Maintain a minimal, non-secret profile registry for listing and default
  selection. Write it atomically and with owner-only permissions on Unix.
- The first successfully stored profile becomes the default. Later imports do
  not change the default. Removing the default selects the lexicographically
  first remaining profile, or clears the default when none remain. An empty
  registry produces an actionable no-profile error; malformed JSON, an invalid
  registered profile, or a default that names no registered profile is reported
  as corruption and is never silently repaired or overwritten.
- Profile names are 1 through 64 ASCII letters, digits, `.`, `_`, or `-`.
- The explicit replacement flag is `--replace-workspace`. Without it, importing
  credentials for a different origin or team into an existing profile fails.
- Profile selection precedence is explicit `--profile`, then
  `LURKLINE_PROFILE`, then the registry default profile. Environment
  credentials, when fully present, override the selected stored profile.
- `--profile` is a Clap global option and is accepted before or after
  subcommands, including the documented `auth import-curl --profile NAME`
  pipeline. Import requires an explicit profile. Status and removal use
  `--profile`, `LURKLINE_PROFILE`, or the default; listing needs no selection.
- Authentication-management commands ignore the four Slack credential
  environment variables. They may use `LURKLINE_PROFILE` only to select a
  stored profile.
- Cross-store mutations follow explicit failure-safe ordering:
  - validate a new session before any mutation;
  - for a new profile, write keyring first and registry second, deleting the
    new keyring entry if the registry write fails;
  - for a same-workspace refresh, update only the existing keyring entry;
  - for `--replace-workspace`, snapshot the previous entry, write keyring first,
    then registry, restoring the previous entry if the registry write fails;
  - for removal, delete the keyring entry first and mutate the registry only
    after deletion succeeds. A retry treats an already-missing keyring entry as
    deleted and cleans stale registry metadata.
  Every primary and rollback failure is secret-safe. A failed rollback reports
  that the profile needs re-import rather than claiming atomicity.
- A missing or unavailable platform credential store must produce a clear,
  actionable error that mentions the environment alternative. Never silently
  downgrade to plaintext storage.
- Keep CLI and MCP behavior backed by the same typed service and resolved
  configuration path.
- Tests and committed fixtures use synthetic domains, identifiers, cookies,
  tokens, and responses only.
- Do not add browser automation, bot/OAuth authorization, write-capable Slack
  methods, a daemon, a database, account synchronization, keyring migration,
  shell completion, registry publication, tags, pushes, pull requests, or
  GitHub releases.
- Implement the smallest coherent complete design. Do not confuse simple with
  partial: the supported platforms, security boundaries, and CLI/MCP parity
  must be explicit and tested.

## Milestone 1: Secure Credential Substrate And Profile Resolution

Why this matters:

- Persistent sessions are safe only if secret storage, precedence, and
  lifecycle behavior are unambiguous before user-facing import is added.

Acceptance criteria:

- A versioned typed credential bundle validates the same origin, team, token,
  and cookie invariants as environment configuration and zeroizes secret
  fields when dropped. Token prefixes are not tightened here; only cURL import
  requires `xoxc-`.
- A credential-store abstraction has a thin native keyring implementation and
  an in-memory synthetic test implementation. Native failures are translated to
  actionable, secret-safe errors.
- A minimal non-secret profile registry supports validated profile names,
  deterministic listing/default selection, atomic updates, owner-only Unix
  permissions, and corruption errors that do not lose existing data. Tests
  cover the first-import default, a later import preserving it, deterministic
  replacement after default removal, empty state, stale defaults, malformed
  JSON, and invalid registered names.
- Resolution implements the documented profile precedence and atomic
  environment override without contacting the native store when any
  environment field is partially configured.
- Existing environment-authenticated commands keep their behavior, and no
  secret-bearing type is cloneable or printable by accident.

Likely touchpoints:

- `Cargo.toml`, `Cargo.lock`, `src/config.rs`, new authentication/profile modules

Verification:

```bash
cargo fmt --check
cargo test auth --locked
cargo test config --locked
cargo clippy --all-targets --locked -- -D warnings
git diff --check
```

Status: Complete on 2026-07-26. Secrets now acquire zeroizing ownership before
partial environment, invalid token/cookie, origin/team, stored-decoding, or
keyring-error returns. Credential-bearing types are not cloneable, native
credential reads are zeroizing by type, and Slack HTTP client clones share one
owned configuration. One versioned JSON bundle is stored per keyring entry;
there is no plaintext secret backend. The non-secret registry validates its
version, profile syntax, normalized workspace origin, team ID, and invariant
that empty state has no default while nonempty state has one registered
default. Writes use an owner-only temporary file, file sync, atomic rename, and
directory sync. First import/default and removal ordering are deterministic.
Linux path logic accepts absolute `XDG_CONFIG_HOME` without `HOME`, falls back

## Milestone 2: Safe Copy-as-cURL Import And Authentication Commands

Why this matters:

- Import should reduce setup to one familiar browser action without turning
  copied developer-tools text into executable code or secret leakage.

Acceptance criteria:

- A bounded restricted lexer handles current Chromium single and ANSI-C quoted
  output and older positional-URL output without executing shell semantics.
- A typed parser extracts supported `--url`, `--data-raw`/`--data`, and
  `-b`/`--cookie` arguments, rejects conflicting duplicates and unsupported
  ambiguity, and decodes URL-encoded form data deterministically.
- Import validates the session before mutation, preserves an existing profile
  if validation or storage fails, and enforces same-workspace refresh versus
  explicit cross-workspace replacement. New, refresh, replacement, removal,
  registry failure, keyring failure, rollback, and stale-metadata retry tests
  enforce the documented cross-store ordering.
- `auth list`, `auth status`, and `auth remove` produce concise human and stable
  JSON output without secrets. Authentication commands run without resolved
  Slack configuration.
- Every authentication subcommand accepts `--json`; `--profile` is global and
  may appear at any subcommand depth. Stable JSON uses these minimal shapes:
  - import:
    `{"profile":"NAME","workspace_url":"ORIGIN","team_id":"TEAM","default":BOOL,"replaced_workspace":BOOL}`;
  - list:
    `{"default_profile":"NAME_OR_NULL","profiles":[{"profile":"NAME","workspace_url":"ORIGIN","team_id":"TEAM","default":BOOL}]}`;
  - status:
    `{"profile":"NAME","workspace_url":"ORIGIN","team_id":"TEAM","default":BOOL,"credential_present":BOOL}`;
  - remove:
    `{"profile":"NAME","removed":BOOL,"default_profile":"NAME_OR_NULL"}`.
- Synthetic unit and process-level tests cover current/older cURL shapes,
  malicious input, bounds, validation failures, keyring failures, update
  semantics, output redaction, and removal.
